# 11 · 短信验证码回传（OTP → 即时通讯）

目标：**人在外面，一条验证码短信进来，几秒内出现在飞书（或你用的任意即时通讯）里**，不依赖你手里那台手机。

这条路和「切卡」「状态回报」共用同一个服务端，只是多一个端点。

## 1. 服务端契约（本项目提供这一半）

```bash
# 写入一条验证码（手机侧调用）
GET /p/<TOKEN>/phone/otp?code=123456&from=YourBank&text=<urlenc 正文>

# 读取最近的几条（内网 / 页面用，公网需 ctl）
GET /phone/otp?n=6
```

行为：
- 带 `code` → 追加到状态文件里的 `otp` 数组（保留最近 **30** 条，字段 `code / from / text / at / src`），并**立刻推一条即时通讯消息**；
- 不带 `code` → 返回最近的 N 条（JSON）；
- 路径必须是 `/p/<TOKEN>/phone/otp`；`/p/<TOKEN>/otp` 会落到通用推送端点，返回 `apprise_status: 404`（踩过）。

推送文案（可自行改）：

```
🔑 验证码｜YourBank 123456
```

## 2. 手机侧怎么把验证码捞出来（三条路线，任选其一）

### 路线 A：短信自动化直传（推荐，零外部依赖）

在手机上建一条自动化：

```
触发器：信息 包含 "验证码"           ← 或运营商/银行的固定关键词
动作：  获取 URL 内容
        GET  https://<push-host>/p/<TOKEN>/phone/otp?code=<…>&from=<发件人>&text=<正文>
```

短板：iOS 的「信息」触发器**拿不到发件人/正文变量**（只有条件匹配），所以只能做到「知道来了一条含关键词的短信」。
两个可行变体：

1. **只报有码**：正文里塞 `code=unknown&from=sms&text=来了一条含验证码的短信` —— 至少你能立刻知道，然后去手机上看；
2. **配合本项目的读屏能力**（路线 C）把真正的 6 位数字补上。

### 路线 B：App 通知直传（验证码类 App / 银行 App 推送）

如果验证码是 App 推送而不是短信，用「通知触发器」（见 [06](06-远程收短信与App通知.md)）把通知正文直接带到同一个端点：

```
GET https://<push-host>/p/<TOKEN>/phone/otp?code=<从通知正文里截>&from=<App名>
```

iOS 的「通知」触发器**能拿到通知正文**，所以在 App 推送场景下这条路线最干净。

### 路线 C：读屏兜底（真的把 6 位数字读出来）

手机连在常开主机上时，用 `iphone-control` 读当前屏幕/通知中心，正则抽 4–8 位数字，再回打 `/phone/otp`：

```bash
# 1) 看当前前台是什么，必要时打开「信息」
ssh host 'python3 scripts/ic_call.py iphone_status "{}"'
ssh host 'python3 scripts/ic_call.py iphone_launch_app "{\"app\":\"com.apple.MobileSMS\"}"'
# 2) 读元素树，找最新一条含「验证码」的文本
ssh host 'python3 scripts/ic_call.py iphone_list_elements "{\"limit\":80}"' | grep -A2 验证码
# 3) 抽 4–8 位数字后回打
curl "https://<push-host>/p/<TOKEN>/phone/otp?code=$CODE&from=<发件人>"
```

> 注意：读屏是**被动**的，需要有人/定时任务去触发；不要为此写死循环轮询，用「短信自动化先报有码 → 主机再读屏补数字」的两段式最省电。

### 路线 D：同 Apple ID 的 Mac 读 `chat.db`（需要另一台已登录同一 Apple ID 的 Mac）

`~/Library/Messages/chat.db` 里能直接查到最新短信原文，正则抽码后回打同一个端点。要求那台 Mac 常开且已登录同一 Apple ID。

## 3. 为什么不在页面上展示验证码

早期版本把最近验证码渲染在页面里，后来去掉了：

- 验证码是**短期凭证**，页面多一个暴露面（截图、浏览器缓存、反代日志）；
- 你本来就只看飞书，即时通讯里有搜索、有历史、有手机通知，比页面好用。

服务端存储只保留 30 条、且只在内存/状态文件里滚动，不做长期归档。

## 4. 安全建议

| 项 | 建议 |
| --- | --- |
| TOKEN | 长随机串，别贴在公开聊天/截图里；怀疑泄露就轮换（手机侧 URL 一起改） |
| 端点暴露 | `/p/<TOKEN>/phone/otp` 必须带 token；`/phone/otp` 只在内网/带 `ctl` 时开放 |
| 转发通道 | 用私聊/私有群，不要用公开频道；群里成员等同能看到你的验证码 |
| 留存 | 保留 30 条上限即可；确认收到后可清空 |
| 双因素 | 验证码本身就是第二因素，**别把「密码 + 验证码」放在同一个通道里** |

## 5. 验证是否通了

```bash
# 写一条假的
curl -s "https://<push-host>/p/<TOKEN>/phone/otp?code=123456&from=TestBank&text=test"
# 期望 {"ok": true, "stored": 1, ...}，并且飞书立刻收到 🔑 验证码｜TestBank 123456
# 读回来
curl -s "https://<push-host>/phone/otp?n=3"
```

收不到就先查：token 对不对 → 端点是不是 `/p/<TOKEN>/phone/otp` → 服务端日志里有没有 `[phone] otp` → 即时通讯通道凭证/群 id 对不对。
