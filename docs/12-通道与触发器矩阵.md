# 通道矩阵：怎么发、怎么收、怎么回

一条远程指令要跑通，链路上有三段通道，都可以换：

```
[发送方式]  服务端 ──→ 手机        （门铃：把指令送到手机上）
[接收方式]  手机侧触发器 + 捷径     （把通知/短信/轮询变成"跑捷径"）
[回传方式]  手机 ──→ 服务端        （把执行结果送回来）
```

**关键事实（iOS 27 起）**：`快捷指令 → 自动化 → 通知` 这条触发器，让**任意 App 的推送**都能当触发器（可选 App + 最多 3 个过滤器：Title / Subtitle / Message，锁屏后台也会跑）。所以 Bark / ntfy / Gotify / 飞书 / Telegram / HA 全部可用，不再局限于短信和邮件。

---

## 一、发送方式（服务端 → 手机）

| 方式 | 一条命令 | 能否直接触发手机 | 备注 |
| --- | --- | --- | --- |
| **iMessage（现役）** | `curl -X POST http://<NAS>:<port>/notify/imessage_nas -d '{"body":"#phone on CARD_A"}'` | ✅ 信息触发器 | 秒级，最稳；依赖一台 Mac/NAS 上的 iMessage 网关 |
| **Email** | `swaks --to you@example.com --server smtp.example.com --body "#phone on CARD_A" --header "Subject: #phone"` | ✅ 邮件触发器 | 抓取模式 5–15 分钟延迟，推送模式几秒 |
| **Bark** | `curl "https://api.day.app/<KEY>/#phone/on%20CARD_A?group=phone"` | ✅ 通知触发器 | 自带重试；body 可放结构化参数 |
| **ntfy** | `curl -H "Title: #phone" -d "on CARD_A" https://ntfy.sh/<topic>` | ✅ 通知触发器 | 自建最省，无需账号 |
| **Gotify** | `curl -X POST "https://gotify.example.com/message?token=<APP_TOKEN>" -F "title=#phone" -F "message=on CARD_A" -F "priority=5"` | ✅ 通知触发器 | 自建、有管理界面 |
| **飞书群机器人** | `curl -X POST "https://open.feishu.cn/open-apis/bot/v2/hook/<HOOK>" -H 'Content-Type: application/json' -d '{"msg_type":"text","content":{"text":"#phone on CARD_A"}}'` | ✅ 通知触发器（App=飞书） | 顺手留下群消息审计 |
| **Telegram** | `curl "https://api.telegram.org/bot<TOKEN>/sendMessage" -d chat_id=<ID> -d text="#phone on CARD_A"` | ✅ 通知触发器（App=Telegram） | — |
| **Home Assistant** | `POST /api/services/notify/mobile_app_<device>` `{"title":"#phone","message":"on CARD_A"}` | ✅ 通知触发器（App=HA） | 可反向由 HA 编排 |
| **webhook / 自建 API** | 任意 HTTP | ❌ 本身不是通知 | 由上面任一 App 转发，或走轮询 |
| **轮询（无发送）** | 不发 | ✅ 时间触发器 | 手机自己每 N 分钟 `pull`，零通道依赖 |

统一层写法（服务端已用 apprise，可一条 URL 搞定）：

```
bark://<KEY>@api.day.app
ntfys://<topic>@ntfy.sh
gotifys://<APP_TOKEN>@gotify.example.com
mailtos://<user>:<pass>@smtp.example.com?to=you@example.com
json://<your-endpoint>/notify
```

## 二、接收方式（手机侧）

| 触发器 | 配置要点 | 无人值守 |
| --- | --- | --- |
| **信息** | 发送者 + 信息包含 `#phone` | ✅ 现役 |
| **邮件** | 主题或正文包含 `#phone` | ✅ |
| **通知**（iOS 27+） | App = Bark/ntfy/Gotify/飞书/HA；`Add Filter` 选 Title 或 Message，填 `#phone` | ✅ 锁屏也跑 |
| **时间** | 每 5 / 15 分钟 | ✅ 轮询兜底 |
| Wi‑Fi / 蓝牙 / NFC / 专注 / 充电 | 场景触发 | ✅（需物理或状态变化） |
| App 打开 | — | ❌ 要人点 |

**通知触发器的两段协议**（比纯文本更干净，省一个号码）：

```
Title:    #phone
Subtitle: （可选）on | off | status | default
Message:  CARD_A
```

捷径里取 `通知` 的 `标题 / 副标题 / 正文` 三个变量 → 走分支 → 执行 → 回传。

**注意**：每个自动化都要过一次「运行前询问」开关（关掉才静默），每张自动化首次运行还会弹一次「允许运行另一个快捷指令吗？」，点一次即永久生效。

## 三、回传方式（手机 → 服务端）

| 方式 | 一条捷径动作 | 说明 |
| --- | --- | --- |
| **HTTP GET（现役）** | `获取 URL 内容` → `https://push.example.com/p/<TOKEN>/phone/report?ok=1&detail=CARD_A&act=on&plan=CARD_A` | 最省，服务端按 act/plan 匹配队列 |
| HTTP POST JSON | 同上改 `方法=POST`、`请求体=JSON`、加 `Content-Type` | 适合带长文本/结构化结果 |
| 飞书 webhook | `获取 URL 内容` POST 机器人地址 | 结果直接落群，不经过自建服务 |
| Bark / ntfy / Gotify | `获取 URL 内容` 打各自 API | 结果当推送发给自己 |
| Email | `发送邮件` 动作 | 离线场景兜底 |
| 短信 | `发送信息` 动作 | 同上 |

## 四、三种开箱配方

**配方 1 · 现有形态（iMessage 门铃 + HTTP 回传）**
```
2999 点按钮 → 服务端入队 → iMessage "#phone on CARD_A" → 信息触发器 → 切换CARD_A → report
```

**配方 2 · 纯 Bark（不占号码，锁屏可跑）**
```
2999 点按钮 → 服务端入队 → Bark 推送(title=#phone, body="on CARD_A")
            → 通知触发器(App=Bark, Message 含 #phone) → 切换CARD_A → report
```

**配方 3 · 零外部通道（定时轮询）**
```
手机每 5 分钟 → GET /p/<TOKEN>/phone/pull?fmt=text
             → 空则退出；有值则执行 → report
服务端只需入队，什么都不用发（PHONE_NUDGE_CHANNEL=none）
```

## 五、服务端配置约定

```bash
PHONE_NUDGE_CHANNEL=imessage|email|bark|ntfy|gotify|feishu|telegram|ha|webhook|none
PHONE_NUDGE_TARGET=<该通道的目标：号码/邮箱/topic/token/webhook URL>
```

- `imessage`：走 `POST /notify/imessage_nas`，正文 `#phone on|off|status <CARD>`
- `bark/ntfy/gotify/feishu/telegram/ha`：`title=#phone`，`message=<verb> <CARD>`
- `none`：不发门铃，靠手机轮询
- 不论哪种，**执行结果的权威判据永远是服务端的 `queue` / `history`**，不是"通知发出去没有"

## 六、排障顺序

1. 触发器有没有跑 → 捷径 App 里看该自动化的「最近运行」时间
2. 跑了但没生效 → `GET /phone/state` 看 `queue` 是否清空、`history` 有无条目
3. 通知有没有到 → 锁屏通知中心里能看到这条推送吗
4. 权限三连 → App 通知权限 / 自动化「运行前询问」已关 / 首次「允许连接 <域名>」已点
5. 键盘类/后台限制 → 低电量模式下触发会延后，属正常

## 八、服务端已实现（2026-11-18）

门铃不再是写死的 iMessage，`_phone_nudge()` 已按通道分派（marker `PHONE_CHANNEL_2026_11_18`）：

```python
def _phone_nudge_channel():
    return ((os.environ.get("PHONE_NUDGE_CHANNEL") or "imessage").strip().lower())
```

| 变量 | 例子 | 说明 |
| --- | --- | --- |
| `PHONE_NUDGE_CHANNEL` | `imessage`（默认）/`bark`/`ntfy`/`gotify`/`feishu`/`telegram`/`email`/`webhook`/`none` | 换通道只改这个 |
| `PHONE_NUDGE_TARGET` | Bark: `KEY` 或完整 URL；ntfy: `topic`；Gotify: `https://host|TOKEN`；飞书: webhook URL；Telegram: `BOT_TOKEN|CHAT_ID`；email: apprise key；webhook: 完整 URL | 各通道格式 |

改法（服务端，systemd 环境变量）：

```bash
sudo systemctl edit push-translator      # 或 push-leg-hw
# [Service]
# Environment=PHONE_NUDGE_CHANNEL=bark
# Environment=PHONE_NUDGE_TARGET=<KEY>
sudo systemctl restart push-translator
curl -s http://127.0.0.1:3020/phone/state | grep -o '"channel": "[a-z]*"'   # 应回显 bark
```

- `none`：只入队不发门铃，日志打 `[phone] nudge skipped channel=none`，手机侧靠「时间」触发器每 N 分钟 `pull`。
- 页面（2999 `/phone`）会自动显示 **当前通道**（`<span id="ph-ch">`），不用再去翻环境变量。
- 通道发失败**不影响**队列：`_phone_nudge` 只记 `[phone] nudge failed via <ch>`，指令仍留在队列等手机轮询或人工触发。
